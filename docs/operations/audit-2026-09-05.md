# 全角色分析与优化报告（2026-09-05）

范围：对 Huoqu 货代取件运营平台做一次“从所有角色出发”的全面分析、测试与优化。
方法：先按角色梳理功能与权限矩阵 → 全量单测/集成回归（98→105）→ 真实容器冒烟 →
Web E2E + 业务旅程 E2E（真实 Chromium）→ 针对发现的真实缺陷做最小改动并回归 → 部署验证。
本报告记录结论、证据与剩余待办（backlog），后续排期可从这里领取。

## 2. 按角色的发现与处置

### 2.1 取件员（现场执行者）
| 发现 | 严重度 | 处置 |
| --- | --- | --- |
| 「邀请协助」在 Web 上可点、后端却只回显原任务：不落库、不通知、不共享权限，看板/我的数据「协助」恒为 0 | 高（功能空壳） | 本轮实现完整协助闭环：`task_assistants` 持久化；`POST /tasks/:id/assist`（v1/v2 一致）真正把任务共享给协助人；协助人可开始/录单/拍照/完成；被邀请人收到站内通知（类型 `pickupTask.assistInvited`，通知设置页可单独开关） |
| 「我的数据」页字段与 `/api/dashboard/me` 返回不一致：页面读 `today/month/assistCount`，接口返回 `pending/inProgress/...`，页面实际长期显示 0 | 高（页面失真） | 重做 `/api/dashboard/me`：返回今日/本月（完成口径：取件次数/客户数/件数/已回填重量）与 `assistCount`，保留旧键兼容 |
| 协助人看不到任务列表/详情，也无法操作 | 高 | 取件员任务查询改为「主取件员 OR 协助取件员」并集；详情、状态、货品、照片权限同步放行 |
| 取件员可借 `POST /tasks/:id/assist` 只凭任务 UUID 读取任何任务详情（越权读取地址/电话/内部备注） | 高（越权） | 仅主取件员或客服/管理员可邀请；无关取件员读取返回 403（v1/v2 同修） |

### 2.2 客服 / 管理员（派单与运营）
| 发现 | 严重度 | 处置 |
| --- | --- | --- |
| 改派/转派/修改/补货/照片上传后无实时广播，其它在线页面不刷新 | 中（协同体验） | 补 `task.updated / task.created` SSE 广播（含 v2 任务动作），详情页与列表页自动刷新 |
| 转派目标取件员不校验存在性（可把任务转给不存在的档案，任务从此无人可见） | 中 | 非空 `workerId` 一律校验存在；转派权限收敛为主取件员或客服+（v1/v2 一致） |
| 看板「协助」列恒 0 | 低 | 按 `task_assistants` 实算（完成口径） |

### 2.3 客户/查单（外部角色）
- 免登录 `GET /api/track` 脱敏查单：旧实现只命中旧 `records`，新任务模型（任务号/业务订单号/明细面单号/手机+姓氏）查不到。
- 处置：本轮改为**双数据源并集**——新任务优先（含明细面单匹配、手机快照+姓氏校验），旧 records 兜底，返回中文状态与统一时间线；新增 1 条查单回归。

### 2.4 安全视角
| 发现 | 严重度 | 处置 |
| --- | --- | --- |
| 登录接口无失败限速，可被爆破（LAN 暴露时更明显） | 中 | 按 用户名+来源IP 记账：15 分钟窗口内连续失败 8 次后 429（v1/v2 共用同一限速器），成功登录清空计数 |
| 全站缺少基础安全响应头 | 低-中 | 全局 `X-Content-Type-Options: nosniff`、`X-Frame-Options: SAMEORIGIN`、`Referrer-Policy: no-referrer` |
| 会话表只在启动清理 | 低 | 运行期每 6 小时定期清理过期会话 |
| SSE 旧入口 `/api/events?token=` 仍存在 | 低（兼容债） | 保留但已带 `Deprecation` 头与日志脱敏；新客户端全部走 `/api/v1/events` ticket。纳入 backlog：下线时间点 |

### 2.5 架构与可维护性视角
| 发现 | 说明 |
| --- | --- |
| v1/v2 双规范层大量重复（`taskVisibleTo`/`taskDetail`/统计 SQL 等） | 本轮两处保持镜像修改以不破坏移动端契约；建议未来收敛为共享 helper（backlog P2） |
| 时间口径混用：任务/明细写入用 UTC 文本，照片/事件/旧记录用北京时间 +8 文本，看板按北京日期截断比较 | 高风险统计隐患：北京 00:00–08:00 与 UTC 16:00–24:00 窗口会把任务算到错误“天”（backlog P1，需要统一存储口径并重跑统计验证，不适合本轮顺带改） |
| 看板 workers/明细存在 N+1 查询 | 当前数据量小无感；数据量大后需聚合 SQL（backlog P2） |
| `POST /tasks/:id/assist` 等“原样返回”式端点暴露过开发期占位实现 | 本轮已全部转为真实语义 |
